# COAP 方法介绍（第一版，供审阅）

> 版本：v0.1（待审阅）｜定位：方法说明文档，与 `src/baseline/COAP/` 已落地的
> 动作缓存模块对应；双路规划编排、评分更新、流式运行等尚在规划中。

## 1. 摘要

COAP 是结合 PPA（Parallelized Planning-Acting）与 ARC（Action Reasoning
Cache）的并行规划方法。它沿用 PPA 的线程化并行架构与记忆模型，引入 ARC 的
动作推理缓存，在**动作执行期间进行定时普通规划**，并在动作结束时以
**双路竞速**（普通规划 vs 缓存动作规划，先得先执行）的方式快速产生下一动作。

系统包含四条并行的运行线路：

1. **动作执行线路**：执行当前动作、轮询状态、处理中断、产出结果反馈。
2. **普通规划线路**：以固定周期在动作执行期间持续产生普通规划结果。
3. **缓存动作规划线路**：在双路竞速时基于缓存候选快速产生动作。
4. **动作缓存管理线路**：缓存初始化、候选暂存、聚合、内容更新、评分更新。

通信上采用**主动通信**（规划输出中的 communication 段，由 LLM 生成）与
**被动通信**（动作反馈广播，直接复用动作结果文本，**不调用 LLM**）。

## 2. 与 PPA、ARC 的关系

| 维度 | PPA | ARC | COAP |
| --- | --- | --- | --- |
| 运行架构 | 线程并行 worker（观测/规划/执行） | asyncio 决策引擎 | 线程并行（同 PPA） |
| 规划触发 | 规划线程持续轮询、有观测即规划 | 动作后立即启动双路 | **定时规划**：动作执行期间按周期规划 |
| 双路规划 | 无缓存路径 | 缓存优先 + 普通规划验证/替代 | **竞速**：普通规划与缓存规划并行，先得可执行动作者执行 |
| 记忆 | TeamMemory（观测/动作历史/聊天通道） | 全局记忆 + 动作历史 | **复用 PPA 的 TeamMemory** |
| 通信 | 主动 chat + 被动 LLM 生成 | 规划输出 communication | 主动通信（LLM）+ 被动反馈广播（无 LLM） |
| 缓存模块 | 无 | Boot/Retriever/Buffer/Update/Score | 引入 ARC 的缓存模块（已抽取） |
| 评分/一致性/流式 | 无 | 有 | 引入 ARC 的评分更新、重要参数对比、流式输出 |

COAP 的目标不是替代 PPA 或 ARC，而是取其各自的优势：PPA 的工程架构与记忆
复用能力，ARC 的缓存驱动低延迟规划能力。

## 3. 系统架构与四条并行线路

```text
                    ┌─────────────────────────────────────────┐
                    │              TeamMemory（PPA 架构）        │
                    │  观测 / 动作历史 / 聊天通道(active/passive/result) │
                    └─────────────────────────────────────────┘
                                   ▲                 │
         写入观测/动作/聊天        │                 │ 读取（prompt 注入）
                                   │                 ▼
┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
│ ① 动作执行线路       │   │ ② 普通规划线路      │   │ ③ 缓存动作规划线路  │
│ ActingWorker       │   │ PlanningWorker     │   │ CachePlanningWorker│
│ 执行/轮询/中断       │   │ 定时触发普通规划     │   │ 双路竞速时触发       │
│ 结果反馈→广播/记忆   │   │ 结果写入下一动作缓冲 │   │ 基于 top-k 缓存输出  │
└────────────────────┘   └────────────────────┘   └────────────────────┘
        │                          │                        │
        │ 上一动作                │ 规划结果                │ 缓存候选
        ▼                          ▼                        ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ④ 动作缓存管理线路 CacheMaintenance                                    │
│ 初始化(Boot) → 候选暂存(Buffer) → 聚合(Aggregate) → 内容更新(Update)    │
│ → 评分更新(Score) → 检索(Retrieve top-k)                               │
└─────────────────────────────────────────────────────────────────────┘
```

四条线路共享 `TeamMemory` 与单槽动作缓冲（`SingleSlotOverwriteBuffer`），
彼此通过事件/缓冲区协作，不存在全局 step / round 屏障。

### 3.1 动作执行线路

负责：

- 从动作缓冲取出规划结果并派发（oneshot 执行 / continuous 启动）；
- 轮询 continuous 动作状态；
- 处理中断（规划产生紧急动作时打断当前连续动作）；
- 动作结束后生成**结果反馈文本**并写入 `result` 通道，同时广播到服务器；
- 将执行结果写回记忆（`complete_action`），供规划与缓存更新使用。

### 3.2 普通规划线路

在动作执行期间以固定周期 `planning_interval`（可配置，默认建议 0.5s）触发
一次**普通规划**。规划输入与 PPA 一致（观测、团队消息、当前动作与结果、
动作空间、任务描述），输出为 ARC 的 `standard_action` 协议
（`{"reasoning","action","interrupt"}` + `<ARC_ACTION_READY>` + 可选
`{"communication"}`）。

输出协议中的 `interrupt` 为布尔标记，用于说明该规划结果是否应立即中断
当前动作；默认 `false`，仅紧急情况为 `true`。

规划结果写入单槽动作缓冲，作为**下一动作候选**；`interrupt=true` 时立即
打断当前动作并派发。

### 3.3 缓存动作规划线路

仅在**双路竞速**时启动（见第 4 节）：从缓存管理线路检索
`top-k` 候选（按上一动作匹配、评分降序），基于候选构建 `cache_action`
prompt（注入候选缓存段），输出 `{"action"}` + marker + 可选 communication，
提示模型优先参考候选（STRICT/ADVISORY 策略）；即使模型选择动作空间中的其他动作，解析也不会因此失败。

### 3.4 动作缓存管理线路

独立线程维护缓存生命周期（本仓库已抽取模块）：

- **初始化**（`CacheBootService`）：`empty` / `llm_init` / `reuse_old` 三种模式；
- **候选暂存**（`CandidateBuffer`）：普通规划结果与执行证据以
  `success / failure / uncertain` 状态暂存；
- **聚合**（`CandidateAggregator`）：按动作转移对聚合统计与 reason 采样；
- **内容更新**（`CacheContentUpdater`）：LLM 抽象通用 reason，创建/更新条目；
- **评分更新**（`ScoreUpdater`，待开发）：按周期统计执行反馈递推评分；
- **检索**（`CacheRetriever`）：供缓存动作规划线路使用。

**候选缓冲的提取（flush）与内容更新触发条件**：

- 缓冲内候选记录条数 ≥ `buffer_size_threshold`（默认 5 条），或
- 距上次 flush 的时间 ≥ `update_interval_seconds`（默认 30 秒）；

两个条件任一满足即触发一次"聚合 → 内容更新 → 评分更新"的批量提取流程，
条数与时间均为可配置参数。评分更新独立于该触发条件：不调用模型，存在
任一待处理反馈即实时触发（由缓存维护线路按约 1 秒轮询消费）。

## 4. 定时规划与双路竞速机制（核心）

COAP 与 PPA 的最大区别在于规划触发方式。设：

- `T`：定时规划周期（`planning_interval`）；
- `buffer`：单槽动作缓冲（保存最新规划结果）；
- `planning_running`：普通规划当前是否正在执行中。

任务开始且尚无活动动作时，先执行一次可执行的普通初始规划。该初始规划
不要求 `interrupt=true`；后续动作执行期间的定时普通规划仍默认只准备下一
动作，动作完成后才进入缓存与普通规划的双路竞速。首轮以前序动作
`START` 检索不到候选属于正常 cache miss，不虚构缓存转移。

### 4.1 动作执行期间的定时规划

当前动作开始后，普通规划线路进入定时循环：

```text
动作执行中
  │
  ├─ 每经过 T 秒 → 触发一次普通规划
  │      └─ 结果写入 buffer（覆盖旧候选）；紧急时可打断当前动作
  │
  └─ 动作结束（自然结束 / 被打断 / 失败）
```

定时规划的目的是让"下一动作"在**动作尚未结束时**就已经开始准备，缩短
动作之间的空档（inter-action gap）。

### 4.2 动作结束时的三种情形

**情形 A：动作结束前，定时规划已完成（buffer 已有结果）**

直接刷新计时并采用 buffer 中的结果作为下一动作，不需要双路规划。

**情形 B：动作结束于下一次定时规划开始之前（buffer 无结果）**

```text
动作结束
  ├─ 刷新定时器（下一轮从 0 开始计时）
  └─ 进入双路规划（此时没有新动作，与 ARC 一致）：
        ├─ 普通规划（从零开始）
        └─ 缓存动作规划（检索 top-k 候选）
        └─ 竞速：哪边先输出可执行动作，就执行哪个
```

**情形 C：动作结束时，普通规划正在进行中**

```text
动作结束（普通规划尚未完成）
  ├─ 不打断该普通规划（让其继续）
  ├─ 同时启动一次缓存动作规划
  └─ 双路竞速：哪边先输出可执行动作，就执行哪个
```

### 4.3 候选缓存记录来源

所有被采用的规划动作，都按以下**动作转移关系**写入候选缓冲，作为后续缓存
提取材料：

- **上一轮刚结束的动作 → 下一轮普通规划输出的动作**（常规转移，覆盖
  情形 A/B/C 中被采用的动作）；
- **中断前的动作 → 中断动作**：当定时规划输出 `interrupt=true` 并打断当前
  连续动作时，记录 (被中断动作, 中断动作) 的转移。

### 4.4 竞速规则

- 两条路径共享同一动作缓冲：先完成并**通过可执行性校验**的动作获胜，立即派发；
- 败方结果不丢弃：若败方是普通规划，其结果按动作转移状态
  （`success / failure / uncertain`）写入候选缓冲，作为缓存更新来源；
- 双路动作使用**重要参数对比**判定一致性（见第 7 节），决定缓存强化与
  候选暂存的状态；
- 若双方都未产出可执行动作（超时或校验失败），进入重规划（最多
  `maximum_replans` 次），并把失败反馈注入下一次规划。

### 4.5 计时器状态机

```text
动作开始 ──► [规划计时中]
               │
               ├─ 到达 T ──► 触发普通规划（planning_running=True）
               │
动作结束 ──► buffer 有结果？ ── 是 ──► 刷新计时，直接采用
               │
               └─ 否：planning_running？ ── 是 ──► 不打断 + 启动缓存规划（竞速）
                                        └─ 否 ──► 刷新计时 + 双路启动（竞速）
```

## 5. 通信机制

### 5.1 chat 动作屏蔽

COAP 已通过规划输出的 `communication` 段实现主动通信，因此**启用 COAP
方法时，`chat.say` / `chat.whisper` 等 chat 动作从动作空间与允许列表中
屏蔽**，不作为 LLM 的候选动作输入；模型不再需要通过 chat 动作发消息，
所有主动通信统一走规划输出的通信段。

### 5.2 主动通信（调用 LLM）

主动通信随规划输出产生：

- 普通规划与缓存动作规划均在输出协议中包含可选 `{"communication": "消息"}`
  段（位于 `<ARC_ACTION_READY>` 标记之后）；
- 通信内容只在**动作可执行且（按策略）执行成功后**提交，写入 `active` /
  `passive` 聊天通道并广播；
- 动作不可执行时，对应的通信内容作废。

### 5.3 被动通信（不调用 LLM）

被动通信 = **动作反馈广播**：

- 每个动作结束后生成紧凑的反馈文本（成功 / 失败 / 中断），格式如
  `执行<简写动作>(参数) 完成/中断/失败：原因`；
- 该文本**不经过 LLM**，直接写入 `result` 通道并广播到服务器聊天记录；
- `result` 通道用于其他 Agent 的上下文与缓存反馈，但在注入 prompt 的
  【团队消息】时按通道过滤，**忽略动作结果记录**，避免刷屏与信息噪声；
- 相比 PPA 的被动通信（Planning 线程基于结果再调用一次 LLM 生成消息），
  COAP 直接复用反馈文本，省去一次 LLM 调用。

## 6. 记忆模块（复用 PPA 架构）

COAP 直接复用 `TeamMemory`，不做新记忆框架：

- **观测**：`update_observation` 持续写入最新观测文本；
- **动作历史**：统一历史事件记录规划、实际选择、状态与结果；
- **团队视角**：自身记录保留完整规划信息，队友只接收主动通信和实际动作
  完成状态，缓存候选、竞速状态、推理和结构化结果不对队友暴露；
- **prompt 注入**：`to_prompt_context` 只提供一个按时间排序的【历史信息】
  区块。历史中的动作调用优先使用动作空间定义的简写，并保留必要的模型
  输入参数。

缓存内容（CacheEntry）单独存储在缓存仓库中，不属于 TeamMemory 的条目。

## 7. 从 ARC 引入的机制

### 7.1 评分更新（ScoreUpdater）

缓存条目维护 `attempt_count / success_count` 与周期增量
`delta_attempt_count / delta_success_count`。评分更新不调用模型，存在任一
待处理反馈即实时触发递推。

**冷启动初始化分数**：

- 缓存初始化（`llm_init`）生成的条目未经环境验证，**初始分数限制在
  (0, 0.5] 区间**（建议 0.05～0.5）；
- 后期通过执行反馈强化（成功则提高、失败则降低）逐步逼近真实成功率；
- 内容更新创建的新条目：有环境证据（success/failure）时可用证据成功率作为
  初始分；无环境证据时使用 `default_uncertain_score`（0.5）作为上限。

**分数更新公式**（反馈驱动递推，与 ARC 一致）：

```text
Δc = delta_attempt_count,  Δq = delta_success_count
r  = Δq / (Δc + ε)                         # 周期成功率（ε 防除零）

# 公式一：置信度调整 + 指数平滑（推荐，周期性批量更新）
α  = λ / (λ + attempt_count)               # 置信度系数，经验越多越信任反馈
score = (1 - α) * score + α * r

# 公式二：增量奖励-惩罚（单次反馈在线更新）
score = score + α * (y - score)            # y ∈ {0,1}，成功=1，失败=0

# 公式三：频率感知（本周期无尝试时的空闲衰减，可选）
score = score * (1 - idle_decay)           # idle_decay ∈ [0,1)，默认 0

score = clip(score, 0, 1)                  # 始终保持在 [0,1]
```

评分仅由初始化与内容更新时设置初值，之后由执行反馈实时递推。冷启动条目
（≤0.5）只有在后续执行成功被强化后才可能超过 0.5，从而避免未经验证的
缓存候选压过有环境证据的条目。

### 7.2 重要参数对比（ImportantParameterActionConsistency）

双路动作一致性判定：

```text
equivalent(left, right) =
    left.name == right.name
    and 对每个配置的重要参数 p：left.parameters[p] == right.parameters[p]
```

用途：

- **双路竞速一致性**：普通规划与缓存规划动作是否一致；
- **候选暂存状态**：与已成功执行动作在名称与全部参数上完全相同才记为
  `success`；仅名称与重要参数一致记 `uncertain`；不一致也记 `uncertain`；
- **缓存强化条件**：缓存动作执行成功，且普通规划动作与缓存动作在重要参数
  上一致时，才对该缓存强化成功计数。

### 7.3 流式运行（Streaming）

规划调用采用流式输出：

1. 要求模型**先输出动作字段**，再输出 `<ARC_ACTION_READY>` 标记，最后输出
   可选的通信段；
2. 一旦解析出完整动作即进行可执行性校验，**无需等待通信段生成完毕**；
3. 动作可执行则其通信有效，动作不可执行则通信作废；
4. 竞速时，流式先完成且可执行的一方获胜。

## 8. 输出协议（沿用 ARC）

| 操作 | 协议 |
| --- | --- |
| 普通规划（定时） | `{"reasoning","action","interrupt"}` + `<ARC_ACTION_READY>` + `{"communication"}` |
| 缓存动作规划 | `{"action"}` + `<ARC_ACTION_READY>` + `{"communication"}` |
| 缓存初始化 | `{"entries":[{index,previous_action,next_action,reason,initial_score}]}` |
| 缓存内容更新 | `{"reason","initial_score"}` |

`interrupt` 标记仅普通（定时）规划输出；缓存动作规划用于动作结束后的竞速
场景，不输出 `interrupt`。动作名为完整动作标识（如 `navigation.goto_position`
或简写映射后的规范名），参数为 JSON 对象。已落地模块：`protocol.py`
（动作协议）、`planning.py`
（初始化/内容更新协议解析）。

   Planning），或暂用缩写；
2. **定时规划周期** `T` 的默认值（建议 0.5s，与 PPA 实测规划间隔一致）；
3. **情形 A 的缓冲采用策略**：动作结束且缓冲已有结果时，直接采用是否还需要
   经过一次可执行性复检；
4. **中断语义**：定时规划结果默认只作为下一动作候选，紧急时才打断当前动作
   （沿用 PPA 的 interrupt 语义），是否确认；
5. **竞速超时**：双路竞速的超时上限与重规划次数（建议沿用 ARC：
   cache 15s / standard 60s / replan 3 次）。
